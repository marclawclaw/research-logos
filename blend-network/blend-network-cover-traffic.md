# Blend Network — Cover Traffic

## Summary

Cover traffic is artificial noise generated by Blend nodes to make real block proposals indistinguishable from dummy messages. It is essential for "hiding in the crowd" when real proposals are rare.

## How Cover Messages Work

- Generated by **core and edge nodes** independently of any real proposal.
- Payload is **random data** — no meaningful content.
- Processed identically to data messages: same encapsulation, dissemination, and random delays.
- **Indistinguishable** from real proposals even to adversary-controlled nodes — the distinction only becomes visible when the final layer of encryption is removed at the last hop.

## Why It Matters

Block proposals are **scarce** by design (one per slot, one winner per lottery). Without cover traffic, the network would be nearly silent between proposals, making any real message trivially identifiable by timing alone. Cover traffic fills this silence.

## Quota Enforcement

To prevent cover traffic from flooding the network:

- Every message (data or cover) must include a **Proof of Quota** in its public header.
- Core nodes verify this proof before relaying.
- Quota caps:
  - Maximum number of messages per sender per session
  - Maximum hops per message (`h_max = 3`)

This maintains **low bandwidth usage** — a key Blend Network design goal vs. general-purpose mixnets.

## Effect on Anonymity Metrics

Cover traffic directly improves:

- **TTL (Time to Link):** Harder to identify which message is a real proposal
- **TTI (Time to Infer stake):** Proposal frequency is obscured by constant noise

Combined with encapsulation and random delays, cover traffic makes the network appear uniformly busy regardless of actual proposal activity.
